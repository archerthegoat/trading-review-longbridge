# 飞书 Wiki 文档数据结构

将 Wiki 设为“讨论、事实摘要和规则”的主库，而非密钥库或未授权原始券商文件仓库。每次写入先在本地生成草稿、由用户确认目标节点与字段范围，再写入并回读。

## Space 与文档创建命令边界

`lark-cli wiki +space-create` 的创建接口只接受 `--as user`；每日信息流没有调用这个命令，而是在已经存在、且 bot 已加入的 space 中写入子文档。交易中心若尚未有独立 space，不得把交易内容写进 `buddy1号 · 每日资讯`，也不得用 bot 绕过 space 创建接口。

## 无独立 Wiki 时的初始化

安装 Skill 不会创建飞书资源。只有在动态发现确认没有交易中心独立 Space 时，才按以下顺序初始化；Space 创建、根节点创建和首次文档写入是三个独立确认门。

### 1. 检查用户授权，不把授权错误当成资源不存在

```bash
lark-cli auth status --json --verify
```

如果返回 `token_missing`、`needs_refresh` 或缺少 Wiki/Docx 权限，先由用户完成授权：

```bash
lark-cli auth login --domain wiki,docs --json
```

授权完成后必须重新运行 `auth status --json --verify`，再开始资源发现。`token_missing` 只表示当前用户 token 无法使用，不证明 Space 或节点不存在。

### 2. 以 user 身份动态发现已有 Space

```bash
lark-cli wiki +space-list --as user --page-all --format json
```

优先复用名称和用途已经明确的交易研究 Space；不得猜 `space_id`，不得把交易中心初始化到其他业务 Space。发现到目标 Space 后，记录返回的真实 `space_id`，不要手工改写或拼接。

### 3. 确认确实不存在后，预演并创建 Space

建议名称为“交易投研中心”，但名称、描述和是否创建必须由用户确认。先预演：

```bash
lark-cli wiki +space-create \
  --as user \
  --name "交易投研中心" \
  --description "交易计划、每日复盘、周度复盘与已确认的研究摘要" \
  --dry-run \
  --format json
```

用户明确确认预演内容后，才去掉 `--dry-run` 执行一次。创建成功后重新运行 `+space-list` 回读，确认名称、`space_id` 和可见性；不重复创建，不使用 bot 身份创建 Space。

### 4. 初始化根节点

先列出根节点：

```bash
lark-cli wiki +node-list \
  --as user \
  --space-id <space_id> \
  --page-all \
  --format json
```

根节点不存在时，先用 `lark-cli wiki +node-create --as user --space-id <space_id> --title "交易中心复盘" --obj-type docx --node-type origin --dry-run --format json` 预演，再经用户确认后创建。创建后重新 `+node-list` 回读并保存真实的节点 token；不得使用 `0`、空值或猜测 token。

### 5. 验证 bot 是否能使用已初始化的 Space

如果自动化需要 bot 创建子文档，必须先由 Space 管理员在飞书中把 bot 加入该 Space，再分别运行 `+space-list`/`+node-list` 的 `--as user` 和 `--as bot` 版本验证可见性。Space 创建成功不代表 bot 已加入；bot 可见性失败时停止写入，不用 raw API 绕过权限。

### 6. 首次文档写入与回读

在真实父节点下创建文档前，先检查精确标题是否已存在；展示 `run_id`、目标节点、标题、正文摘要和字段范围，用户确认后才执行：

```bash
lark-cli docs +create --as bot --doc-format markdown \
  --parent-token <parent_node_token> \
  --title '<标题>' \
  --content @draft.md \
  --format json
lark-cli docs +fetch --as bot --doc <document_token> --doc-format markdown --format json
```

写入后必须回读标题、正文、revision 和 `permission_grant`。文档创建成功但权限授予失败时，分别报告两种状态，不能合并成“Wiki 初始化成功”。`docs +create` 的 Markdown 内容应遵循当前 `lark-doc` 规则，长内容优先用当前工作目录下的 `@draft.md` 文件传入。

### 失败处理

- `token_missing`、`needs_refresh` 或缺少 scope：先重新授权，不创建替代 Space。
- Space 列表成功但没有目标 Space：保留“未初始化”，等待用户确认创建，不自动执行写入。
- Space 存在但根节点或 bot 不可见：补齐节点/成员权限并重新回读，停止自动化写入。
- 写入成功但回读失败：报告“部分完成/回读阻塞”，不得输出“已写入并核验”。

目标 space 已经存在时，按每日信息流的可复用方式操作：

```bash
lark-cli wiki +node-list --as bot --space-id <space_id> --page-all --format json
lark-cli wiki +node-list --as bot --space-id <space_id> --parent-node-token <parent_node_token> --page-all --format json
lark-cli docs +create --as bot --doc-format markdown --parent-token <parent_node_token> --title '<标题>' --content - --format json
```

每次创建前先按精确标题列出父节点子文档；同名则跳过，不覆盖旧文档。`docs +create --as bot` 成功后，CLI 可能另外尝试给当前用户授予 `full_access`；这项授予失败不等同于文档创建失败，必须分别读取返回中的 `document` 与 `permission_grant` 状态。空间不存在、bot 未加入或父节点无法读取时，停止写入并报告阻塞。

## 建议树

```text
交易投研中心
├── 00 数据契约与权限
│   ├── 数据源登记册
│   ├── 字段分级与脱敏规则
│   └── 导入与写入日志
├── 01 每日交易记录
│   └── YYYY/MM/YYYY-MM-DD｜日常记录与复盘
├── 02 周度复盘与下周规划
│   └── YYYY/YYYY-WW｜本周复盘与下周规划
├── 03 周度账户与操作汇总
│   └── YYYY/YYYY-WW｜账户价值、持仓变化与操作摘要
├── 04 交易规则与洞见
│   ├── 已验证规则
│   ├── 待验证假设
│   └── 常见错误与修正规则
└── 05 交易想法、计划与市场日程
    ├── 交易想法卡
    ├── 周度计划版本记录
    └── YYYY-WW｜观察池、前提、失效条件与风险
```

## 所有记录的共同头部

每个日/周文档开头固定记录：`记录 ID`、`期间与时区`、`数据源 ID`、`授权状态`、`数据状态`、`覆盖范围`、`缺失项`、`最后更新`。数据源 ID 只指向数据源登记册，不放账户号、令牌、原始文件名或凭据。

## 数据源登记册

每个来源一条记录，字段为：来源名称、来源类型（用户录入/本地导出/公开数据）、允许用途、授权范围、可用字段、覆盖范围、刷新频率、数据状态、保管位置、禁止写入字段、最后核验时间。Longbridge 条目在用户明确授权前应为 `未读取`。

## 记录分级

| 级别 | 可写内容 | 写入规则 |
| --- | --- | --- |
| L0 | 市场研究、观察池、规则、用户主动提供的非私密叙述 | 用户确认文档内容后写入 |
| L1 | 周度账户价值变化、持仓/操作的最小聚合 | 需本线程导入授权及写入确认 |
| L2 | 标的、数量、价格、成本、订单/成交明细 | 逐字段说明用途后单独确认 |
| L3 | API key、密码、令牌、Cookie、完整原始导出 | 永不写入 Wiki、Git 或 Skill |

## 交易中心默认写入边界

Wiki 的默认职责是保存“经过讨论并确认、以后还需要复用的结论”，不是保存每次运行的完整数据流。每次写入预览必须把内容分为三类：`本次写入 Wiki`、`只保留私有运行目录/当前对话`、`需要逐字段确认后才能写入`。

| 内容 | 默认去向 | 是否写入 Wiki | 说明 |
| --- | --- | --- | --- |
| 用户确认的交易想法、触发/确认/失效规则、仓位分散原则 | 交易想法卡 / 交易规则与洞见 | 是，L0 | 记录状态、证据来源和最后确认时间；未确认内容留在待验证窗口 |
| 当前有效周度计划、周中版本变化、每日 `D1/D2` 增量 | 周度复盘与下周规划 / 周度计划版本记录 | 是，L0 | 写版本号、变更摘要和用户确认；不覆盖历史版本 |
| 每日/周度复盘结论、计划 vs. 实际的解释、纪律问题和后续问题 | 每日交易记录 / 周度复盘 | 是，L0 | 只写讨论后确认的结论，不把脚本草稿或推测当结论 |
| 与观察池直接相关的公开事件摘要 | 每日交易记录 / 市场日程 | 是，L0 | 只选相关事件，保留日期、时区、来源和数据状态；不复制整段新闻或完整日历 |
| Longbridge 持仓/操作的方向和标的级最小聚合 | 周度账户与操作汇总 | 仅在本线程导入授权 + 写入确认后写，L1 | 可写计数、方向、标的级聚合和数据覆盖说明；不能从聚合推断完整账户 |
| Longbridge 原始订单/成交、精确数量/价格/成本、当前持仓明细、订单/成交 ID | Git 工作树外的私有运行目录 | 默认不写；如需写入必须逐字段确认，L2 | 复盘展示可以在当前对话中使用，但 Wiki 默认只保留 L1 聚合 |
| 完整市场事件/新闻馈送、机械脚本原始输出、未确认分析草稿 | 私有运行目录 / 当前对话 | 否 | 只从中提炼已确认的 L0 事件摘要 |
| 盘中关注点 | 当前对话 | 否，默认不写 | 它是当天的临时观察清单；只有用户明确把某条升级为计划/规则变更时，才以 L0 变更写入 |
| API key、密码、令牌、Cookie、账户标识和完整原始导出 | 永不保留到 Wiki/Git/Skill | 永不写 | 仅在授权范围内短暂用于必要的本地调用 |

### 一次复盘的 Wiki 写入包

每个自动化创建的新复盘对话均是独立 `run`，不需要主对话。写入预览必须列出 `run_id`、目标节点和字段范围；当三者没有未解决问题，用户在该 `run` 内说“复盘完成”（或等价明确确认）时，默认写入包只包含本轮增量：

1. 记录元数据：记录 ID、期间与时区、数据源类型、授权状态、数据状态、覆盖范围和缺失项。
2. 已确认的当日/周度复盘结论：计划 vs. 实际的解释、执行分类、纪律问题和下一步讨论项。
3. 已确认的计划版本或每日增量：变更摘要、触发/失效规则、用户确认状态和版本号。
4. 相关公开事件的最小摘要：事件名称、日期/时区、来源和状态。
5. L1 账户/操作聚合（若本次已取得对应导入授权）：只写必要的标的级方向/计数和数据缺口，不写原始明细。

写入前的预览必须同时列出“明确不写入”的原始券商明细、当前持仓数量/成本、订单/成交 ID、完整新闻馈送和临时盘中关注点。

### “复盘完成”确认信号

在交易中心自动化中，“复盘完成”不是仅表示草稿生成，而是对**当前独立 `run`** 已展示的增量写入包作确认，并授权将该包写入已展示的 Wiki 节点。该确认不要求来自主对话，亦不可用于另一 `run`。若用户只说“看过了”或只确认某一条事实，不触发写入；若 `run_id`、目标节点、计划版本或 L2 字段仍有疑问，先补问并保持待确认状态。

### 跨任务完成状态

复盘与盘中关注点是两个 standalone 任务，后者看不到前一任务的聊天确认。因此，复盘任务在 Wiki 写入并回读成功后，必须由**同一独立 `run`** 在当前 `records/weekly/<ISO-week>-trading-plan.md` 的每日增量区域追加不含券商明细的流程标记：

```text
run_id=<本轮标识>；复盘状态=已完成；增量/版本=<本轮标识>；Wiki状态=已写入并回读核验；完成时间=<Asia/Shanghai>
```

该独立 `run` 可以创建当前 ISO 周记录或追加当前周的新版本，不需要主对话；但必须先解析精确目标，不得回写历史周或覆盖既有文本。盘中关注任务还要只读核对在线 Wiki 的目标节点，确认同一 `run_id`、增量/版本确实存在并能回读。仅有聊天中的“复盘完成”、旧 Wiki 版本、或本地写入草稿/未经匹配的“已写入”描述，都不足以放行；本地状态与在线 Wiki 不一致时，标记“状态不一致”并停止。

## 文档职责

- **每日交易记录**：计划、观察、过程、每日复盘和待确认事项；不强制包含券商事实。
- **周度账户与操作汇总**：脚本计算的价值变化、持仓变化与操作聚合，使用 [周度账户与操作汇总模板](../assets/weekly-portfolio-and-operations-summary.md)。
- **周度复盘与下周规划**：讨论后的结论、过程复盘、规则与下周观察，不将其混同于原始导入。
- **交易规则与洞见**：只收录经用户确认的规则，标明证据来源和验证状态。
- **交易想法、计划与市场日程**：想法经讨论后直接进入待验证窗口；周度计划保留基线和周中版本变化。失效想法归档，并保留最小失效记录。

## 写入顺序

`本地私有导入 -> 生成 run_id 并解析当前 ISO 周目标 -> 脚本生成聚合草稿 -> 展示本轮增量写入包 -> 用户在本 run 说“复盘完成” -> Wiki L0/L1（必要时逐字段 L2）追加写入 -> 回读核验 -> 由同一 run 写入流程标记 -> 输出盘中关注点`。AI 如被允许，只作用于用户确认的文本范围，生成的内容必须标注模型、时间和“待人工确认”。Wiki 写入或回读失败时，不进入最后的盘中关注阶段。

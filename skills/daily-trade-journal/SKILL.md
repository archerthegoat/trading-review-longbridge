# 每日交易日记

把本 Skill 当作一个以用户叙述为中心的普通 Markdown 记录入口，而不是交易执行、计划对齐或账户看板。它维护两组内容：`持仓管理` 和 `计划买入`。每个标的只记录交易工具与具体想法；触发、退出、加仓或减仓条件如果有，就自然写在想法里，不另设必填字段。期权方向统一写英文 `Call` / `Put`。

## 日常工作流

1. 先发现并读取 `25 投资交易` 中的当前计划记录、相关旧日记和当天旧记录，尊重已有手写内容、历史想法和当前落点，不臆造新的真相源。若只有旧不可变计划版本而没有普通计划落点，先向用户确认目标和承接范围，不静默迁移。
2. 再听用户本次对当日交易想法、等待原因或计划变化的叙述。已有回答不重复问，只追必要缺口；没有当日叙述时不能自行编出日记，也不能用任务活动替代用户叙述。
3. 把本轮确认的内容整理到 `持仓管理` 或 `计划买入`。清楚区分用户自述与已核验事实；券商数据暂缺时仍可如实记录用户想法，但不能把自述标为独立核验的成交、持仓或行情事实。
4. 先展示具体 Markdown 草稿，说明尚未写入。用户说出“确认写入”后，才保存已确认部分；没有变化时返回 `no_op`。

不强制结果评价、固定问卷或机械的计划内/计划外标签。未实施的想法可以继续有效；已买入不代表 `持仓管理` 结束；跨周仍有效的内容沿用，不自动重建、清空或失效。对未来动作保留“考虑”“可能”等原语气，不自动升级为确定执行；新建或修订仅在展示具体内容并得到用户确认写入后保存，不强制新版本或固定问卷。

## 技术面边界

只有在用户讨论某个标的且需要参考时，才提供轻量支撑、压力或条件判断。默认只使用真实来源的已完成 1D 日线，并注明来源、截至时间和周期；资料不足就明确说不能判断。用户目标价不是已验证压力位，触价不是成交，日线结论不是小时级验证。小时观察由用户自行查看；用户口述的小时观察只能保留为自述。

可按需使用已有的只读行情能力，但本 Skill 不引入下载器或依赖，也不把技术分析做成日记前置步骤。原有只读成交或合约辅助工具可以保留作可选参考；不得强制机器投影、不可变新版本或 schema 才能记普通日记，也不得声称旧程序已经变成普通记录引擎。既有不可变版本只作只读历史参考，本轮不原地覆盖或迁移真实记录。

## 周末回顾

周末只回顾本周已经发生的操作和计划实施情况，分别说明已实施、仍等待和缺少证据。仍有效的计划跨周沿用；只有用户明确确认作废，才把具体对象单独展示并归档到现有私有知识库体系。归档不直接删除、不自动失效，归档也需要独立确认。本轮只验证周度行为说明，不创建或修改定时任务；Skill 支持生成周末回顾，调度配置须另获授权，现有自动化未声明同步。

## Obsidian 写入与隐私

继续使用现有目录：

- `25 投资交易/10 每日复盘`
- `25 投资交易/20 周度复盘`
- `25 投资交易/30 已确认计划摘要`

写入前保留可恢复的原版本，重读 live 文件并检查并发变化；未开始写时如有冲突，保留原文并停止。已有 managed 日记只在既有 managed 边界内更新；没有 managed 的普通计划笔记只改用户确认的段落，保留其他手写内容，不强制新建 managed 区域或 schema。写后先做文件系统回读，再按顺序做 Obsidian CLI 回读；回读失败就停止后续写入并报告写入未验证，不宣称成功或自动回滚。需要回滚时先重读，发现新修改不得覆盖。草稿、测试、配置读回和旧自动化状态都不等于真实写入或人类验收。

沿用既有隐私边界：不把账户、盈亏、原始券商响应、凭据或敏感记录写入仓库、普通日志或公开日记；不访问或恢复 Web UI、SQLite、Bridge，不下单，也不进行真实记录迁移。具体期权合约身份只在已有的、明确授权的私有预览边界内处理，不因本 Skill 扩大授权。

## 失败状态

数据缺失、来源过旧、事实无法核验、并发变化或回读失败时保持 `blocked`、`PENDING` 或 `NOT RUN` 等真实状态，并说明缺口；不能把缺数据当成无成交、不能把自述当成核验事实。实施、自动化、测试、外部写入和人类接受分别报告，互不升级状态。

# daily-trade-journal v2 架构报告

## 1. 当前目标、批准范围与证据状态

本报告记录用户已确认的第一批 daily-trade-journal Skill 重构。当前日记入口从“先展示核对、再采访、把普通交易抽象成 Set”调整为：

- Obsidian 是唯一长期、可恢复的持久化边界；
- 同一复盘上下文被中断时，可发现并核对脱敏临时草稿，但不能把它自动升级为真源；
- 每日第一个面向用户的阶段是采访；
- 实际交易先按动作和顺序逐条记录，再做用户叙述、事前确认计划和实际盘面的三方对齐；
- META、SNOW、QQQ 默认是普通交易上下文，不因同一标的、多次动作或期权自动成为多腿 Set；
- 完整 PA 不每日自动运行，只在制定或更新计划、或用户指定交易复盘时触发；
- 宏观研讨由用户主题、昨日判断和用户看到的消息驱动定向搜索，并在逻辑审查后更新宏观环境/形态判断，不生成固定新闻日报；
- 最终草稿必须经过当前用户明确“确认写入”，并完成写前并发检查、文件系统回读和 Obsidian CLI 回读后，才能标记 written。

本批只修改以下仓库文件：

- skills/daily-trade-journal/SKILL.md
- skills/daily-trade-journal/references/storage-and-recording.md
- skills/daily-trade-journal/agents/openai.yaml
- docs/architecture/daily-trade-journal-v2.md

本批不修改 Obsidian Vault、确认计划版本、每日复盘、private temp、脚本、测试、README、路线图、自动化配置或 Git 历史；不抓取 Longbridge、新闻或行情，不进行真实外部写入，不新增数据库、UI、Bridge、outbox 或第二持久化系统。

本报告中的本地检查、Skill 校验和静态差异检查属于自动化证据，不等于真实 broker fact、真实宏观检索、真实 Obsidian written 或人类验收。真实 Longbridge、新闻搜索、PA 运行、Obsidian 写入和人类验收仍须单独标记为 NOT RUN 或 PENDING，不能由本地检查升级。

## 3. 唯一长期存储边界

### 3.1 真源表

| 内容 | 唯一真源 | 规则 |
| --- | --- | --- |
| 事前确认计划 | Obsidian 25 投资交易/30 已确认计划摘要/版本/*.md | 版本不可变；只选确认时间不晚于相关交易或观察时间的版本 |
| 计划导航 | Obsidian 25 投资交易/30 已确认计划摘要/已确认计划摘要.md | 只用于人工导航；机器不能只读导航文件得出计划结论 |
| 每日复盘 | Obsidian 25 投资交易/10 每日复盘/YYYY-MM-DD.md | 用户确认写入且两阶段回读成功后，是该日期的唯一复盘真源 |
| 周度复盘 | Obsidian 25 投资交易/20 周度复盘 下的既有笔记 | 只汇总已经写入的每日复盘，不反向覆盖每日事实 |
| 当前运行中间态 | /private/tmp/trading-center-review-runtime/<run-id>/ | 不是事实真源；中断后只允许作为同一复盘上下文的脱敏恢复候选 |

每日日期文件不存在只代表尚未写入，不能表示没有计划、没有交易或没有用户记录。Skill、脚本输出、预览和架构报告都是操作材料，不在仓库建立每日复盘竞争副本。

### 3.2 临时态生命周期

临时目录在一次运行开始时创建，保存完成本次采访和草稿所需的最小信息。正常完成并写回 Obsidian 后应记录已消费关系，再在安全检查点清理或标记过期；清理失败不改变其非权威性质。

临时态必须保持 owner-only，不上传、不提交、不同步到 GitHub。它可以帮助当前运行跨越采访、证据整理和草稿展示；中断后也可以由同一复盘日期、明确任务、时间和脱敏状态建立恢复候选，但不会改变 Obsidian 真源，也不能绕过用户确认和写后回读。

### 3.3 中断恢复与冲突顺序

本次故障证据表明：已有确认计划版本和旧临时草稿都可能保留此前讨论，而每日日期文件尚未创建。只检查每日日期文件会把“尚未写入”误判为“从未讨论”。仓库文档不记录具体标的、价位或账户信息。

恢复算法保持以下顺序：

1. 读取最新适用的 Obsidian 确认计划版本和目标每日笔记；
2. 在用户继续同一日期/任务或明确要求找回时，定位脱敏临时候选；
3. 只读取摘要、草稿、状态或 manifest，排除原始券商 payload、日志、账户数据和凭据；
4. 以 Obsidian 已确认内容为权威，将临时内容标为已覆盖、候选或冲突；
5. 向用户展示最小差异，确认后只恢复讨论上下文，不升级为计划或交易事实；
6. 在新的当前运行目录继续，旧候选保持不变；最终写入仍需明确确认和两阶段回读。

无法建立稳定关联、来源不清或包含敏感原始数据时停止读取正文并标记 blocked。旧候选不因年龄自动删除，也不能因为修改时间较新就覆盖已确认内容。

## 4. 日常流程与状态转换

### 4.1 采访优先

提问前可以静默读取上一份每日复盘、适用计划和经范围筛选的未完成草稿候选，先恢复已经可靠表达过的用户输入。第一个面向用户的阶段仍必须是采访，但只询问尚未恢复或存在冲突的内容，不重复询问已被确认版本或经用户核对的恢复内容。采访阶段收集：

- 昨天实际发生的交易及其动作顺序；
- 每笔交易的上下文、触发、犹豫和原因；
- 用户看到的消息、想讨论的宏观主题和要验证的判断；
- 是否要制定/更新计划，或复盘某一笔交易。

采访阶段不得先展示计划对齐结论、PA 结论或预先写好的交易判断。交易问题可以收敛，但固定问题上限不能阻断用户主导的宏观研讨。

### 4.2 用户回答后收集证据

用户回答后，才读取交易事实、盘面和研究证据；确认计划和恢复候选可在采访前静默读取以减少重复提问。证据范围包括：

- 适用的不可变确认计划版本；
- 上一完成美股交易日的必要只读交易事实；
- 与交易窗口对应的已完成盘面数据；
- 用户请求的宏观来源或定向搜索结果；
- 用户明确要求的 PA 所需证据。

计划版本必须满足确认时间门槛。来源缺失、时间不适用、版本冲突、动作或工具不完整时保持无法核对或 blocked，不用旧导航、候选观察或用户事后叙述代替确认版本。

### 4.3 逐条交易优先于归纳

每日复盘先建立“昨日实际交易”区块，逐条保留用户叙述的动作、顺序、标的、工具类别和上下文，再单独添加计划提及与计划对齐。

计划提及只有四个值：明确计划、仅上下文、未提及、无法读取。

计划对齐只有三个值：按计划、偏离计划、无法核对。

仅上下文不能升级为明确计划；未提及不能自动判为偏离；缺少交易事实不能自动判为没有交易；无法验证不能自动判为按计划。三方对齐是事后解释，不产生新的交易授权。

#### 明确分组时的 Set 生命周期

META、SNOW、QQQ 默认是普通交易上下文。只有用户明确把动作分组，或确认计划本身明确建立了分组，才进入本节的 Set 生命周期。即使进入 Set，也只表示计划语义；仍需保留每个成员的逐条动作，且不能变成后台执行状态或自动下单授权。

### 4.4 三方对齐

每条交易都按以下顺序呈现：

1. 用户叙述：实际做了什么、动作顺序、当时上下文和原因；
2. 事前确认计划：是否明确提及标的、动作、工具和条件；
3. 实际盘面：已完成周期、数据来源、截至时间、可见走势和市场反应。

然后分别写支持点、冲突或反例、缺失证据和对齐结论。用户叙述不是数据事实，盘面推断不是成交事实，计划描述也不是实际成交事实；任何一方缺失都保留缺口。

### 4.5 宏观研讨

用户提供主题、昨日判断、消息或链接、待验证问题中的任一项或部分输入即可启动定向宏观研讨；不要求四项齐全；只有完全没有任何宏观讨论输入时才跳过搜索。

进行研讨时，先保留用户原始判断、确定程度和时间尺度，再把可核验主张转成搜索问题。搜索必须围绕用户已有输入定向进行：

- 核验事件、政策或数据的发布时间和截至时间；
- 补充直接相关的官方资料和高可信报道；
- 把市场反应与原因分开；
- 寻找支持证据、反例和相反解释；
- 指出事实错误、因果跳跃、时间尺度错配，以及从宏观直接推导个股或期权的过度推断。

在与主题相关的维度内，综合判断增长与通胀组合、政策与利率/流动性、风险偏好及其传导链，不机械填满固定宏观仪表盘。宏观区块必须分开记录用户原始判断、核验事实、市场反应、逻辑审查、分析推断、更新后的宏观环境/形态判断、反证和不确定性，并记录来源、发布时间或数据截至时间。宏观观点只作为每日复盘背景；若它改变具体标的、动作、工具或条件，必须另行形成并确认新的计划版本。

### 4.6 PA

普通每日复盘不自动运行完整 Al Brooks PA。只有以下任务触发 PA：

- 制定新交易计划；
- 更新既有交易计划；
- 用户指定某笔交易进行复盘。

PA 输出区分用户自述、数据事实和分析推断，并给出观察窗口、条件和失效条件。周期、来源、截至时间或 K 线完成状态不足时标记 NOT RUN、PENDING 或 blocked。测试、配置读回或盘面摘要不能替代 PA 证据，标的方向也不能直接转换为期权盈利结论。

### 4.7 草稿和确认写入

交易记录、三方对齐及用户要求的宏观或 PA 研讨完成后，先展示 Markdown 草稿并声明尚未写入。用户未明确说“确认写入”时，状态保持 awaiting_confirmation，不接触 Obsidian。

收到当次明确确认后：

1. 重读目标日期的 Obsidian live note，保留用户已有内容；
2. 检查内容版本、修改时间或等价并发信号；
3. 有并发变化则停止、展示差异并重新确认，不覆盖新内容；
4. 只写入用户确认的每日复盘段落；
5. 先做文件系统回读，再做 Obsidian CLI 回读；
6. 两次回读都成功后才能标记 written，否则标记写入未验证。

## 5. 记录契约

每日日期文件可以使用一个可定位的 daily-trade-journal managed block，并保留用户手写内容：

~~~markdown
---
type: daily-trade-review
review_date: YYYY-MM-DD
plan_source: 25 投资交易/30 已确认计划摘要/版本/<version>.md
daily_note_state: not_written | written
broker_fact_state: complete | empty | blocked
draft_recovery_state: none | candidate | reconciled | conflict | expired | blocked
journal_state: interview_required | awaiting_confirmation | written
---

<!-- daily-trade-journal:start -->
## 昨日实际交易
## 我的交易叙述
## 事前计划与交易对齐
## 实际盘面
## 宏观研讨
## PA 复盘或计划更新
## 下一步与待确认事项
<!-- daily-trade-journal:end -->
~~~

交易字段、计划提及/对齐、三方对齐、宏观字段、PA 状态和隐私边界的详细规则统一放在 skills/daily-trade-journal/references/storage-and-recording.md，避免在入口和架构报告之间出现多套字段定义。

## 6. 状态和失败矩阵

| 状态轴 | 允许值 | 不能推出的结论 |
| --- | --- | --- |
| plan_source | found、missing、conflict、blocked | 不能推出实际成交或计划执行；仅上下文只属于 plan_mention |
| draft_recovery | none、candidate、reconciled、conflict、expired、blocked | 不能推出确认计划、成交事实或最终日记；修改时间较新也不能覆盖 Obsidian |
| daily_note | not_written、已存在、blocked | not_written 不能推出没有交易或没有来源 |
| broker_fact | complete、empty、blocked | complete 不能推出计划匹配；empty 不能覆盖查询范围外的事实；blocked 不能降级为无成交 |
| journal | interview_required、awaiting_confirmation、written | 草稿、测试或 CLI 成功不能推出 written |
| macro | not_discussed、unchanged、updated、partial、blocked | 宏观观点不能自动生成买卖或期权方向 |
| PA | NOT RUN、PENDING、complete、blocked | 配置或静态检查不能推出 PA complete |
| plan_mention | 明确计划、仅上下文、未提及、无法读取 | 仅上下文不能升级为计划 |
| plan_alignment | 按计划、偏离计划、无法核对 | 缺失或不完整证据不能推出按计划或偏离 |

输入缺失、来源过期、时间无效、字段冲突、权限失败和外部依赖缺失时，保留原始原因以及 partial/blocked 状态。不得把缺失写成无交易、无持仓、无计划或已完成分析。

## 7. 隐私与范围

最终每日笔记可以保存用户的交易叙事、判断、上下文、来源、状态和三方对齐，但不得保存：

- 原始券商响应、账户或请求标识、订单/成交 ID；
- 精确数量、价格、费用、余额、盈亏或凭据；
- 完整期权身份、完整代码或可还原账户身份的组合字段；
- 为了“原样”而复制的敏感 provider payload。

面向当前用户的预览可以保留用户亲口叙事和必要上下文的原样表达，但不能把原始券商 payload、账户/订单/成交标识、完整期权身份等敏感结构化字段带入长期笔记、Git、共享输出或 private temp；不得越过隐私边界。private temp 也不能成为长期存储或 GitHub 内容。

本 Skill 不负责选股、交易执行、账户管理、计划迁移、自动化配置、路线图修改或其他研究任务。它不以本次重构为理由修改现有 parser、tests 或其他 Skill。

## 8. 历史实现事实与本批边界

此前的 v2 实现曾包含以下历史实现事实和既有代码行为：

- `al-brooks-pa` 面向已筛选标的，以 1D 作背景、1H 作执行参考，并要求来源、`as_of`、周期和已完成 K 线状态；缺少这些证据时保留缺口。
- 此前投影在内部解析 `OptionContract.right`，按 `review_date` 机械区分 `0DTE 期权` 与 `其他期权`，公开投影保持脱敏，不暴露完整期权身份。
- 此前现有脚本支持复用 `intraday_revisions` 已采集输入；脚本不调用券商，也不写入 Obsidian。
- QQQ 日内 Set 是历史最小场景，仅在明确确认版本中作为当日计划模式，不建立 UI、数据库或后台执行状态。

上述内容是历史实现事实，不代表本批新增 parser、schema 或真实运行授权；本批不修改这些脚本、测试或其他 Skill。本次文档修订明确调整其编排优先级：

- 旧的“先展示 broker facts 再采访”不再是当前用户流程；
- QQQ 等标的不再默认被描述为 Set；
- 完整 PA 不再作为每日复盘的固定后续步骤；
- 宏观不再作为固定日报，而是用户主题驱动的研讨；
- local JSON、preview 和脚本输出不再被视为每日复盘真源；其中脱敏草稿只可在同一复盘上下文中作为恢复候选。

本批没有真实迁移旧计划或日记，没有真实 Longbridge/新闻/行情运行，没有真实 PA 调用，没有真实 Obsidian 写入，也没有记录人类验收 PASS。任何这些事项在后续运行中都必须单独取得授权并按证据层报告。

## 9. 维护、回滚和未决风险

本批的回滚边界是四个仓库文件的文档变更；不涉及 Obsidian 文件、临时目录、账户数据或 Git 历史重写。若后续要让脚本强制执行新的逐条交易、宏观或三方对齐字段，必须先单独确认 schema、迁移、测试和兼容性，不从本批文档自动推导。

未决风险包括：

- 运行时是否稳定提供确认时间、动作和工具字段；
- 实际交易事实与用户叙述如何在不泄露敏感字段的前提下持续对齐；
- 盘面数据的周期、来源、截至时间和完成状态；
- 旧临时草稿是否能稳定关联到同一复盘日期或明确任务，以及恢复候选如何标记已消费；
- 定向宏观搜索的来源可用性和市场反应归因；
- 用户“确认写入”的表达是否明确；
- Obsidian 写入前并发检查及两阶段回读是否可用。

这些风险保持 PENDING/NOT RUN，不能由文档校验或本地单元测试升级。路线图仍由人控制，本批未修改。
